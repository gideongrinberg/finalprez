Technical Overview

Stock Data

  • We use five years of tick data with a uniform tick size of five seconds
    • Impractical to store this much data in memory
  • Data is generated into the database using Python
  • Loaded and processed on backend on-demand, updated via WebSockets

Gideon The most important thing in our trading app is, of course, the stock data. Because of the costs associated with granular data, we decided to use synthetic data. Although it would have been possible to use less granular data for free, using this level of granularity was a more technically interesting challenge.

We originally generated the data in-memory, but we realized that, once we scaled up to multiple stocks over long-year periods, it would actually crash the app, so we ended up pre-generating the historical data and then generating the new data on the server and pushing updates to clients over WebSockets. This was another challenge, because we needed to process the data into candlesticks on the server in order to minimize latency.

Technical Overview

Data Generation

  • Data generated using geometric Brownian motion, standard for simulating stocks

\[ S_t = S_0 \exp\left( \left( \mu - \frac{1}{2} \sigma^2 \right)t + \sigma W_t \right) \]

  • \(\mu\): Drift (expected return)
  • \(\sigma\): Volatility of the asset
  • \(W_t\): Standard Brownian motion

Jackson This is the equation we used to generate the stock price data. S sub t represents the price at a time t, and S sub zero represents the time at the start. Basically, the equation combines a long-term drift with short term volatility. The mu represents the average return which is the rate of the drift, and the sigma represents the volatility.

Data Generation (Code Walkthrough)

def simulate_gbm_ticks(...) -> pd.DataFrame:
    if seed is not None:
        np.random.seed(seed)

    total_ticks = ticks_per_day * trading_days_per_year * years
    dt = 1 / (trading_days_per_year * ticks_per_day)  # Time step in years

    # Generate Brownian increments
    dW = np.random.normal(loc=0.0, scale=np.sqrt(dt), size=total_ticks)
    W = np.cumsum(dW)

    # GBM formula
    t = np.linspace(0, years, total_ticks)
    drift = (mu - 0.5 * sigma**2) * t
    diffusion = sigma * W
    S = S0 * np.exp(drift + diffusion)

    # Create timestamps (approximate, no weekends/holidays)
    timestamps = pd.date_range(start='2020-01-01', periods=total_ticks, freq='S')
    df = pd.DataFrame({'timestamp': timestamps, 'price': S})

    return df

Jackson This is the code we used to generate data based on geometric Brownian motion. Here at the top, we calculate the number of ticks in a year, and then we use that to figure out delta T, the time between ticks. That allows us to scale the GBM equation from years to ticks.

[advance]

The next thing we do is take a series of normally-distributed random values and sum them, which gives us the random noise for each tick. This is what’s called the Brownian motion

[advance]

And then we create the actual price data. The first line here creates the time grid, which is just the list of ticks. Then, we calculate the drift and diffusion for each step and plug them into the GBM formula to generate the price data.

One thing you’ll notice is that we’re not using any loops here even though t, W, and S are all lists. We’re using numpy, which allows us to do scalar multiplication without a loop. It makes the code easier to understand, and it’s faster than looping, which turned out to be important because we were generating so much data.

[advance]

Anyway, once we have the list of prices, we use Pandas to generate timestamps for each tick, and then we save it to a Parquet file. Parquet is basically a compressed version of CSV, and we needed to use it because the final data for all the stocks took up over a gigabyte as a CSV.

Gideon To choose the tech stack for this project, we wanted to find tools that were popular in the professional world, but also modern and easy to use. We settled on React with TypeScript for our web framework. React is by far the most popular framework for modern web apps, and TypeScript adds static type checking to JavaScript, which makes it way easier to use. You get fewer runtime errors and better IDE autocomplete, as well as better LLM integration.

For the styling, we used Tailwind, which is a CSS library, along with components from the shadcn/ui library, which is maintained by Vercel and used by their agentic design tool V0. To handle authentication and database hosting, we used Supabase, which provides a hosted Postgres instance with a lot of features for easy authentication.

We also used the lightweight-charts library, which is the free version of the charting tool that powers TradingView. Their enterprise SDKs are used by a lot of major companies, like brokerages and crypto exchanges, so it’s a really powerful tool.

LLM Usage

The Key Takeaways

  • Chatbots (e.g., ChatGPT, Claude):
    Great for self-contained tasks like data generation

  • Hosted agents (e.g., Replit Ghostwriter, Lovable):
    Effective for building full-stack apps and bootstrapping projects

  • Self-hosted agents (e.g., Claude Code, Cline):
    Promising, but limited by setup complexity and context constraints

  • Learned more about strengths and weaknesses of LLMs, how to use them effectively.

*Jackson One of the main goals of this project was obviously to learn, and one of the things we wanted to learn about was how to effectively use LLMs in coding. We tried, essentially, three categories of LLMs: chatbots, which are the standard web-based LLMs, hosted agents like Repl.it and Lovable, and then self-hosted agents like Claude Code and Cline.

Each of these have distinct uses – the chatbots were really helpful for self-contained stuff like the data generation, but they struggle with bigger codebases. The hosted agents, especially Loveable, are really fine-tuned for making web apps, so they turned out to be really useful as we were starting out. One big takeaway was that you need to be able to identify the limitations of these tools and know when to step in. For example, basically every tool we tried struggled to integrate the lightweight-trading SDK, even when we provided documentation, so we eventually intervened manually and wrote that code.

This project definitely gave us a lot of insight into prompt engineering and how to combine LLMs effectively into our development workflows.

Gideon Here we can see how routing is implemented in the application. The BrowserRouter provides routing functionality, with the AuthProvider wrapping everything to make authentication available throughout the app. The RequireAuth component is a protected route wrapper that ensures only authenticated users can access the main application routes. Each major section of the app has its own route, with the StockDetail route taking a dynamic ticker parameter to display specific stock information. This setup creates a user-friendly navigation structure while ensuring proper access control.
